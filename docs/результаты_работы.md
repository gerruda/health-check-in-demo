## 1. Задача и границы этапа

Запрос владельца: создать **основу** бота (репозиторий, каркас, тесты, статический
анализ, документацию) в `бот/health-check-in`; саму бизнес-логику не писать —
достаточно одного хендлера `/help`, чтобы проверить, что бот запускается и
отвечает. Следующим шагом владелец создаст закрытый репозиторий, подключит его
к этой папке и будет развивать фичи этапами через пулл-реквесты.

Сделано именно это: работающий скелет на long polling с `/help`, конфиг из
`.env`, логирование, allowlist по `chat_id`, unit-/интеграционные тесты,
golangci-lint + go vet + gofmt/gofumpt/goimports, CI-workflow, README и этот отчёт.

Бизнес-логика M1–M4 (чек-ины, тренировки, питание, замеры, статьи, настройки)
**сознательно не реализована** — под неё подготовлены пакеты и точки расширения
(см. §6 и §8).

## 3. Как это работает

### Поток запуска

`main` → `signal.NotifyContext(SIGINT/SIGTERM)` → `app.Run(ctx, dryRun)`:

1. `config.Load()` — читает `.env` (если есть), затем переменные окружения
   (caarlos0/env v11), применяет дефолты и валидирует `LLM_MODE`, `LLM_FALLBACK`,
   API-креды, `DATA_ROOT`, `BOT_PROXY_URL`. Наличие `BOT_TOKEN` проверяется
   отдельно (`RequireBotToken`), чтобы `-dry-run` работал без токена.
2. `logging.New(LOG_DIR, BOT_TOKEN, LLM_API_KEY)` — JSON-логи в
   `logs/healthbot.log` + stderr, формат `[пакет:метод] суть на русском`,
   секреты маскируются централизованно (NFR-3.1/3.2).
3. В лог пишется `cfg` (реализован `slog.LogValuer`): токен и API-ключ **не**
   попадают в логи, только флаги `bot_token_set`/`llm_api_key_set` (NFR-1).
4. `-dry-run` — прогон `/help` через in-memory `Sender`, затем выход 0 (CI smoke).
5. Иначе — `telego.NewBot(BOT_TOKEN, WithHTTPClient(прокси), WithLogger)` →
   `GetMe` (проверка токена/прокси + аккаунт в стартовый лог, NFR-3.3) →
   `UpdatesViaLongPolling(ctx, nil)`.
6. Каждое обновление → `router.HandleUpdate`: не-сообщения игнорируются;
   allowlist отсекает чужие `chat_id` (только лог); `/help` → справка;
   неизвестная команда → подсказка.
7. Свободный текст → `router.answerWithChat` (FR-6.7): агент LLM с инструментами;
   модель может вызвать `read_last_checkin` (последний чек-ин из файловой БЗ),
   после чего отвечает в чат; ошибка LLM → fallback-текст, бот не падает.
8. Любая паника в обработчике изолируется (`handleSafely`) — бот не падает.
9. Ctrl+C/SIGTERM → контекст отменяется → long polling завершается, канал
   обновлений закрывается → graceful shutdown.

### Ключевые интерфейсы (для следующих этапов)

- `router.Sender` — минимальная часть `telego.Bot` (`SendMessage`); позволяет
  тестировать обработчики без Telegram (ТЗ §12).
- `router.Router.HandleUpdate(ctx, telego.Update)` — единая точка входа для
  апдейтов. Сюда на M1 будет подключена классификация (intake → nlu → analysis).
- `router.Allowlist{Athlete, Wife}` — два chat_id из `.env`; пустые значения
  выключают фильтр (локальная отладка).
- `router.Chatter` — интерфейс LLM-чата в роутере (`Ask`); реализация —
  `llm.Agent` (провайдеры + tool-loop), связывание в `internal/app`.
- `llm.Provider` — `Chat` + `Extract` (FR-6.1); `tools.Registry` — инструменты
  и их JSON-схемы для модели.
- `config.Config` — все поля из ТЗ §9 уже есть (DataRoot, LogDir, LLM_*),
  доменные пакеты могут получать их как зависимости.

### 4.1 govulncheck

`govulncheck` прогоняется в CI-джобе `vuln` и локально через `make vuln`.
Первый прогон нашёл 2 CVE в транзитивных зависимостях telego
(`andybalholm/brotli` v1.2.2, `klauspost/compress` v1.19.1). Зависимости
обновлены до исправленных версий (`brotli` v1.2.7, `compress` v1.20.2,
явно зафиксированы в `go.mod`). Повторный прогон: **`No vulnerabilities found`**.

### 4.2 Живой запуск в Telegram (через прокси)

Проверено 2026-11-11 после подключения репозитория и выдачи токена. Из РФ прямой
доступ к `api.telegram.org` заблокирован (curl напрямую — FAIL, через прокси —
OK), поэтому без прокси `make run` не подключался, а `make dry-run` проходил
(он принципиально не ходит в сеть). Добавлен `BOT_PROXY_URL`; прогон через
`http://127.0.0.1:12334`:


## 5. Принятые решения и отклонения от ТЗ

1. **Объём этапа — `/help` + LLM-чат** (по заданию владельца). Остальные
   команды FR-5 (`/start`, `/checkin`, `/status` и т.д.) не реализованы.
   В `router.HandleUpdate` для них есть заготовка: неизвестная команда отвечает
   подсказкой про `/help`; свободный текст уходит в LLM-чат (FR-6.7), после M1
   классификация FR-1.1 решит, когда вызывать LLM (FR-1.2).
2. **`.env`-лоадер свой, на stdlib** (`internal/config/dotenv.go`): caarlos0/env
   читает только переменные окружения, а `.env` нужен для `make run` из ТЗ §9.
   Парсер поддерживает комментарии, `export`, кавычки и **не перезаписывает**
   уже заданные переменные окружения. Тесты — `config_test.go`.
3. **`DATA_ROOT` по умолчанию `../..`**: бот живёт в `health/бот/health-check-in`,
   на уровень глубже, чем в ТЗ (`health/бот`). При другoм размещении задаётся в `.env`.
4. **`LOG_DIR=logs`** относительно каталога запуска (т.е. `бот/health-check-in/logs/`);
   каталог в `.gitignore`. В ТЗ NFR-3 путь указан как `бот/logs/` — сдвиг из-за
   вложенности репозитория.
5. **`-dry-run`** добавлен как самопроверка/CI smoke (в ТЗ §12 упомянут
   «smoke-запуск с `--dry-run`»). Без токена и без сети.
6. **Модуль `healthbot`** (как в ТЗ §9). Это не URL-путь репозитория: после
   создания приватного репо можно оставить как есть или переименовать
   (`go mod edit -module github.com/<org>/<repo>` + замены импортов
   `healthbot/internal/...`) — отдельной задачей PR.
7. **yaml.v3 не подключён** пока: появится на M2 вместе с `бот/настройки/*.yaml`
   (FR-7). `go mod tidy` удаляет неиспользуемые зависимости, поэтому добавление
   сейчас было бы мусором.
8. **gofumpt и module-path**: путь модуля `healthbot` не содержит точки, и
   gofumpt *как библиотека* без `module-path` считает `healthbot/...`
   стандартной библиотекой, ломая группы импортов (golangci-lint падал на
   ложных «not properly formatted»). Поэтому в `.golangci.yml` явно задано
   `formatters.settings.gofumpt.module-path: healthbot`. **Не удалять** — иначе
   `make lint` начнёт ругаться на импорты.
9. **CI** содержит lint/test/vuln и dry-run smoke. Ежемесячный `deps-update`
   job (ТЗ §9) не добавлен — имеет смысл после подключения репозитория к GitHub
   (нужны права на PR). Добавить отдельным PR.
10. **allowlist по умолчанию выключен**, если оба `chat_id` = 0 (чтобы можно было
    отладить до выдачи ID). В прод-конфиге заполнить оба ID — чужие сообщения
    тогда игнорируются (ТЗ §2).
11. **Токен в логах telego**: кастомный логгер telego не подключался намеренно —
    его debug-логи могут содержать URL с токеном. Наши логи содержат только
    безопасные поля (NFR-1).
12. **Транзитивные CVE telego закрыты** обновлением `brotli`/`klauspost/compress`
    в `go.mod` (см. §4.1) — это осознанный выход за пины telego, безопасно для
    минорных версий; при обновлении telego перепроверить `make vuln`.
13. **Локальный git-репозиторий** инициализирован (`main`, один initial commit):
    следующий шаг владельца — создать приватный remote и запушить (команды в §8).
    Автор коммита — нейтральный bootstrap-identity; при желании переписать:
    `git commit --amend --reset-author`.
14. **Прокси для Telegram API** (`BOT_PROXY_URL`, 2026-11-11): из РФ прямой доступ
    к `api.telegram.org` заблокирован — без прокси `make run` не подключается,
    при этом `make dry-run` проходит (он не ходит в сеть; это и объясняло
    расхождение). Поддержаны схемы `http`, `https`, `socks5`; пусто — прямое
    подключение (переменные `HTTP(S)_PROXY` из окружения намеренно игнорируются,
    источник истины — конфиг бота). В лог пишется только `scheme://host` — пароль
    прокси (если есть в URL) не утекает. Живой запуск проверен через
    `http://127.0.0.1:12334` (см. §4.2).
15. **Формат логов** (`[пакет:метод] суть на русском`, 2026-11-11): сообщения
    собираются через `logging.Msg("pkg:Func", "текст")`, например
    `[app:Run] запуск healthbot`, `[router:HandleUpdate] сообщение от постороннего
    chat_id проигнорировано`. Подробности — в attrs (`chat_id`, `update_id`,
    `proxy`), поэтому по логу видно пакет/метод-источник и данные. Ошибки telego
    идут через адаптер с префиксом `[telego:api]`; штатная отмена long polling —
    debug, не ERROR. Токен и ключи маскируются централизованно в slog-хендлере
    (`***`), в т.ч. в тексте ошибок; ошибки в stderr тоже санитизируются.
16. **Стартовый лог аккаунта**: при запуске вызывается `getMe` (таймаут 15 с) —
    проверка токена/прокси и запись `[app:Run] бот запущен на аккаунте @username`
    (+`bot_id`). Без `getMe` инстанс не стартует: сразу понятно, если токен/прокси
    не работают (NFR-3.3). Обновлена спека: NFR-3.1–3.3, §10, тест-кейсы
    U15–U17, I10, E5.
17. **LLM-провайдеры FR-6** (2026-11-11, v0.2.0): `llm.Provider` = `Chat` +
    `Extract`; Ollama (`/api/chat`, native `tool_calls`, `format` для Extract) и
    OpenAI-совместимый API (`/chat/completions`, Bearer, tool_calls); fallback по
    `LLM_FALLBACK`; таймаут 20 с; логи `[llm:ollama|api]` без текста сообщений.
18. **Скриншоты (FR-6.8)** (2026-11-12, v0.3.0): vision-провайдер отдельно от
    чата (`LLM_VISION_MODE/MODEL`, внешний API — `LLM_VISION_API_URL/KEY`);
    `Provider.ExtractVision` (Ollama `images`+`format`, OpenAI `image_url`);
    скриншоты обрабатываются по одному изображению на вызов, результаты
    объединяются; альбомы (`media_group_id`) собираются 1.2 с; текстовый чек-ин —
    сначала детерминированные правила, LLM — fallback; дата дословно
    (`date_text`) переводится кодом; таймаут vision 180 с; память — вызовы
    сериализуются, модель выгружается после теста.
19. **Чат и инструменты** (FR-6.7): свободный текст → `llm.Agent` с tool-loop
    (≤4 шага); инструмент `read_last_checkin` читает последний по дате чек-ин,
    шаблоны игнорирует; ошибка LLM → вежливый fallback-текст. Отдельно — CLI
    `-ask` для живого смоука модели/инструментов без Telegram. Модель по
    умолчанию `qwen2.5:3b` (FR-6.2/ТЗ v1.4); спека дополнена FR-6.7,
    тест-кейсами U18–U23/I11–I12/E7.

## 7. Процесс разработки для следующих агентов

1. **Сначала спека, потом код (SDD, ТЗ §11):** правка `ТЗ_телеграм_бот.md` §3–§7
   (FR с номером и критериями приёмки) → тест-кейсы в §13 → код.
2. **TDD (RED→GREEN→REFACTOR):** сначала падающий тест минимального поведения,
   потом реализация, потом рефакторинг. На баг — воспроизводящий тест.
3. **Тесты без сети:** unit — чистые функции, integration — обработчики с
   fake `Sender` + `t.TempDir()` как `DATA_ROOT`, LLM-фикстуры в `testdata/`,
   HTTP — `httptest.Server` (ТЗ §12).
4. **Definition of Done:** `make check` зелёный (fmt-check + vet + lint + test),
   обновлены ТЗ (если менялось поведение) и этот файл/MEMORY; PR с описанием.
5. **PR-процесс:** каждая фича — ветка от `main`, PR, CI обязателен, ревью.
   Ветку не пушить напрямую в `main` без PR (после подключения репозитория).
6. **Безопасность:** токены/ключи — только `.env`; в логи не писать тексты
   сообщений и секреты; `gitleaks` в pre-commit; при `LLM_MODE=api` помнить,
   что тексты уходят внешнему сервису (FR-6.5).
7. **Окружение:** на обычной машине `make` работает как есть. В ограниченной
   песочнице (read-only `$HOME`) Go-кэши перенаправляются внутрь workspace:
   `GOPATH=<repo>/.sandbox-cache/gopath`, `GOCACHE=<repo>/.sandbox-cache/gocache`,
   `GOLANGCI_LINT_CACHE=<repo>/.sandbox-cache/golangci-lint`
   (каталог в `.gitignore`, в репозиторий не попадает; локальные артефакты
   `.sandbox-cache/`, `.bin/`, `bin/`, `logs/`, `coverage.out` можно удалить).

не попадают (`.gitignore`, pre-commit gitleaks).
