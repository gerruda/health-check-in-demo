# Ручное тестирование healthbot: кейсы и тест-план

**Версия бота:** `main` после мержей от 2026-11-14
**Кто:** атлет (chat 1), жена (chat 2), чужой chat (если есть)
**Режим:** реальный Telegram, локальные Ollama + `nomic-embed-text`, форматы
Markdown-хранилища.

**Разбор найденных багов и правила против повторения:** [`incident-lessons.md`](incident-lessons.md).

## 0. Подготовка и безопасность

1. Перезапустить бота на актуальном `main` (`make run` или systemd).
2. Обновить меню команд в BotFather (см. `docs/botfather/commands.txt`).
3. **Сделать бэкап данных** — ручные тесты пишут в реальные файлы:
   ```bash
   cd /home/flash/work/PDF/health
   cp -a данные_пользователя данные_пользователя.backup
   cp -a данные_жены данные_жены.backup
   cp -a база_знаний база_знаний.backup
   cp -a настройки настройки.backup 2>/dev/null || true
   ```
4. Перед серией: `make check && make e2e` — базовая линия.
5. Тестовые сообщения ниже можно копировать целиком.

Что уже покрыто автоматикой (не тратить ручное время на дубли):
`make e2e` — команды/формы через реальный router; unit — парсеры, зоны,
прогрессия, store, scheduler. Ручной тест — про **реальный Telegram, LLM,
vision, данные и UX**.

## 13. Известные ограничения (не баги)

- Форма `/checkin` пока не содержит женских полей (МЦ/колени/голод/ходьба) — они работают свободным текстом.
- Питание жены пока не учитывает фазу МЦ по углеводам.
- 4-недельная стратегическая сводка ещё не реализована (только недельный `/review`).
- Формы живут в памяти: рестарт посреди формы теряет ввод.
- В дневнике-отчёте тренировки длительность не выводится отдельной строкой (данные сохраняются).
- Заполнение `база_знаний` статьями — отдельный backlog, не M3.
- Авторазбор воскресенья по умолчанию выключен.
- Если дата на скриншоте тренировки не распознана — бот предупредит и сохранит на текущую дату; для другой даты пришли текст.
- Повторная отправка того же скриншота после успешной обработки игнорируется (дедупликация 10 минут).
- Модель qwen2.5:3b может путать креатин/креатинин и иногда даёт неточный ответ — это quality-ограничение, не потеря данных.

## 14. Критерии выхода

- Все P0 кейсы — PASS.
- P1 — PASS или зафиксированы понятные known issues.
- Нет потери/порчи данных, нет смешивания профилей.
- Все команды из `/help` работают.
- `make check` и `make e2e` зелёные.
- Нет новых ошибок в `logs/healthbot.log` (кроме ожидаемых fallback).
