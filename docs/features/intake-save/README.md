# Фича: интеграция приёма и сохранения (intake → store)

**Ветка:** `feat/intake-save` · **Статус:** готово к PR (проверки зелёные) · **Дата:** 2026-11-12
**Связанные пункты ТЗ:** FR-2 (сохранение), FR-6.8.5 (ответ), §6 (`Checkin`/`Nutrition`), §13 (I1–I7, U13).

## 1. Зачем

Замкнуть цикл: пользователь прислал чек-ин/скриншот → бот распознал → **сохранил
критичные данные** в файловую БЗ (`данные_*/ежедневные_чекины/YYYY-MM-DD.md`) →
подтвердил в чате путь и дату (ДД.ММ.ГГГГ). Пока цикл замыкался только на ответ.

## 2. Что сохраняем

**Критичные поля (пишем в файл):** сон (`SleepH`), HRV, пульс покоя, настроение,
алкоголь (дозы/заметка), вес, шаги, план тренировки; для жены — день/фаза МЦ,
колени, голод, постпрандиальная ходьба; контекст.

**Анализ-only (НЕ пишем в чек-ин):** усталость, температура, цель нагрузки —
маленькая модель их распознаёт, они участвуют в анализе/ответе, но в `nlu.Checkin`
их нет. Питание — отдельным объектом, секцией «Питание» в чек-ине за дату питания.

## 3. Acceptance criteria

| # | Критерий | Проверка |
|---|---|---|
| AC1 | `intake.Saver` + `WithSaver`: после успешного распознавания вызвать `SaveCheckin`/`SaveNutrition`; ошибка сохранения не отменяет ответ, добавляет «Не удалось сохранить» | `intake/save_test.go` |
| AC2 | Маппинг `Extracted` → `nlu.Checkin`/`nlu.Nutrition`: критичные поля сохраняются, temp/load/fatigue — нет | save_test + файл |
| AC3 | Дата: из распознанной (`2026-11-11`) иначе сегодня; файл `YYYY-MM-DD.md`; в ответе «Сохранено: <относительный путь>» | save_test |
| AC4 | Человек по `chat_id`: `WithPersonResolver` — атлет/жена; по умолчанию атлет; файлы не смешиваются | save_test |
| AC5 | Нет saver → прежнее поведение (ответ «Сохранение — на M1»), ничего не пишется | save_test |
| AC6 | Повторная отправка того же чек-ина не дублирует строки (merge writer, I2) | integration-тест с реальным store |
| AC7 | `app`: saver поверх `store.Writer`, пути относительные для ответа; `WithPersonResolver` от chat_id конфига | сборка/ручной прогон |
| AC8 | `make check`/`-race`; спека/README/отчёт; PR | CI |

## 4. Архитектура

```
intake.Service (после Extract)
  → save(extracted, chatID): person=resolver(chatID), date=ex.Date|today
  → toCheckin/toNutrition (критичные поля)
  → Saver (интерфейс) → app.storeSaver → store.Writer (atomic + merge)
  → ответ: FormatReply(extracted, paths...) + предупреждение при ошибке
```

- `intake` не импортирует `store`: только интерфейс `Saver` + модели `nlu`.
- `app.storeSaver` — тонкий адаптер `store.Writer`; для ответа отдаёт путь
  относительно `DATA_ROOT` (`данные_пользователя/ежедневные_чекины/…`).
- Даты: файлы — ISO, ответ — ДД.ММ.ГГГГ (см. предыдущую фичу).
- Идемпотентность/merge — на стороне `store.Writer` (уже реализовано).

## 5. Тесты

| Тест | Что проверяет |
|---|---|
| `TestServiceSavesCheckinFromText` | правила текста → saver.checkin (HRV/RHR/Sleep), ответ «Сохранено» |
| `TestServiceSavesNutritionFromImage` | vision-питание → saver.nutrition (ккал/макро) |
| `TestServiceSavesBothFromAlbum` | альбом питание+готовность → оба сохранения |
| `TestServiceSavesWife` | resolver по chat_id → person=wife |
| `TestServiceSaveDateFromProvider` | дата из LLM (`2026-11-11`) |
| `TestServiceSaveError` | ошибка saver → «Не удалось сохранить», ответ не падает |
| `TestServiceNoSaver` | нет saver → прежний текст (M1) |
| `TestServiceSaveIdempotent` | два одинаковых сообщения → файл без дублей |
| `TestFormatReplySaved` | «Сохранено: путь», без «M1» |

## 6. Что НЕ входит

- Подтверждение перед сохранением (сохраняем сразу, правки — «поправка:» merge).
- `/set`, `/status`, HRV_7 из reader — следующие инкременты M2.
- Сохранение не-критичных полей (температура/цель нагрузки).
