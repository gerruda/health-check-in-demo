# Фича: LLM-провайдеры (Ollama / OpenAI-совместимый) + чат и инструменты

**Ветка:** `feat/llm-providers` · **Статус:** готово к PR (проверки зелёные; финальный E2E в чате — после запуска) · **Дата:** 2026-11-11
**Связанные пункты ТЗ:** FR-6 (LLM-провайдеры), FR-1.2 (LLM-фолбэк), NFR-1/NFR-2/NFR-3, §13.

## 1. Зачем

Каркас (M0) содержит только `/help`; провайдеры LLM из FR-6 не были реализованы.
Эта фича закрывает FR-6 и даёт первую полезную интеграцию:

1. **Простой ответ модели в чат**: пользователь пишет обычный текст — бот отвечает
   через LLM (Ollama локально; внешний API — по выбору `LLM_MODE=api`).
2. **Ответ из чата в модель** — тот же путь, но проверяется CLI-смоуком `-ask`
   без Telegram.
3. **Вызов инструмента**: модель может вызвать `read_last_checkin` — прочитать
   последний по дате чек-ин из `данные_*/ежедневные_чекины/` и ответить по его
   содержимому (пример: «какой там HRV?»).

Место крутится локально: Ollama `http://127.0.0.1:11434`, модель **`qwen2.5:3b`**
(проверено: модель отдаёт `tool_calls` в native-формате Ollama).

## 3. Архитектурные решения

- **Native tool calling вместо парсинга JSON из текста.** Ollama (qwen2.5:3b)
  возвращает `message.tool_calls` с объектом аргументов; результаты инструментов
  отправляются сообщением `role:"tool"` (+ `tool_name`). Это надёжнее, чем
  «попроси модель вернуть JSON-протокол в тексте».
- **Единый внутренний контракт** (`llm.Message`, `llm.ToolCall`), в проводе —
  маппинг под формат провайдера (Ollama: arguments объект; OpenAI: строка JSON).
- **Провайдер не знает про Telegram и данные.** `internal/llm` — сеть LLM;
  `internal/tools` — инструменты поверх файловой БЗ; `internal/router` — только
  интерфейс `Chatter` (без импорта llm), связывание в `internal/app`.
- **Деградация:** ошибка LLM не роняет бота (NFR-2): лог + короткий ответ
  пользователю; fallback по FR-6.4; таймаут 20 с на вызов (FR-6.6).
- **Приватность:** в лог — только провайдер/модель/латентность/размер ответа;
  текст сообщений не логируется (NFR-1/FR-6.6); секреты маскируются (NFR-3.2).
- **Свободный текст → LLM** — временная точка расширения: после M1 классификация
  (FR-1.1) будет решать, когда вызывать LLM (FR-1.2). Сейчас некомандный текст
  уходит в LLM, если провайдер сконфигурирован.
- **Смоук без Telegram:** флаг `-ask` — аналог `-dry-run` для LLM: строит
  агента из `.env` и печатает ответ (проверка модели/прокси/инструмента).

## 5. Живая проверка (локальная Ollama)

```bash
# 1) простой ответ модели
go run ./cmd/healthbot -ask "Ответь одним предложением: кто ты?"

# 2) инструмент: чтение последнего чек-ина
go run ./cmd/healthbot -ask "Какой HRV в моём последнем чек-ине?"

# 3) чат в Telegram
make run   # написать боту «привет» — ответ модели; «что по сну?» — tool call
```

Ожидание: (1) осмысленный русский ответ; (2) модель вызывает
`read_last_checkin`, бот отвечает по содержимому последнего файла (сейчас
`2026-11-03.md`); (3) то же в Telegram. Без Ollama бот живёт, но на текст
отвечает «модель недоступна».

## 6. Что НЕ входит в фичу

- Классификация/парсинг чек-инов и writer (M1) — отдельная фича.
- `Extract` в прод-пути (настройка/парсинг) — только интерфейс + тесты; будет
  использован на M1.
- FSM-формы, `/status`, настройки — M2/M4.
- Внешний API по умолчанию не включается; `LLM_MODE=api` — только осознанно.
