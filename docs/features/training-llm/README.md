# Фича: LLM-извлечение тренировки под шаблон + уточняющий вопрос

**Ветка:** `feat/training-llm` · **Статус:** готово к PR · **Дата:** 2026-11-12
**Связанные пункты ТЗ:** FR-1.1 (свободная форма), FR-2.2/2.7 (файлы/пропуск), FR-3.3 (разбор — частично), FR-6.1 (structured extract), FR-8 (голос).

## 1. Зачем

Детерминированный парсер хорош для форматов «60x5x5», но люди пишут свободно:
«суставная разминка, подтягивания 3 раза, все по 3 подхода, кардио лестница
32 этаж». Нужна универсальность: модель разбирает текст в **структуру шаблона
дневника**, код валидирует, при нехватке данных бот задаёт **один** уточняющий
вопрос. Правила остаются fallback (офлайн/сбой/дешёвый путь).

## 2. Как работает

```
/training / текст-тренировка
  → rules ParseTraining (структура, дата, тип, RPE, кардио)
  → LLM TrainingExtractor (JSON schema под шаблон)
      → validate/normalize (тип, даты, диапазоны, боль)
      → needs_more?  → один вопрос в чат, без сохранения
  → merge: правила — база структуры; модель дополняет упражнения/поля
  → store.Writer → Итог/Упражнения/Кардио/Самочувствие/Боль
  → ответ «Ритма» + путь
  → при ошибке LLM → правила; если и они не справились → подсказка формата
```

- Схема: `kind`, `date_text`, `duration_min`, `avg_hr`, `rpe_session`,
  `exercises[{name,weight_kg,sets,reps,rpe,note}]`, `cardio`, `felt`, `pain`,
  `done`, `needs_more`.
- Промпт: «не выдумывай веса/повторы», «названия дословно», «все по N подходов
  → sets=N всем», «кардио/лестница — не упражнение», «один вопрос максимум».
- `date_text` переводится кодом (вчера/сегодня/11 ноября), а не моделью.
- Тип нормализуется кодами файлов (`ulichnaya`, `sila-A`, `MC2_silovaya`…).
- Валидация: диапазоны RPE/пульса/длительности, вес, боль 0–10; пустые
  упражнения отбрасываются; `done=false` — пропуск.
- Merge: если правила нашли упражнения — доверяем их составу и добираем
  недостающие поля из модели; если правилам нечего дать — берём список модели.
  Это защищает от галлюцинаций small-модели и сохраняет универсальность.

## 3. Acceptance criteria

| # | Критерий | Проверка |
|---|---|---|
| AC1 | `TrainingExtractor` парсит JSON в `nlu.Training`, дата/тип/поля | `training_llm_test.go` |
| AC2 | `needs_more` → один вопрос, без сохранения | service test |
| AC3 | Ошибка LLM → детерминированные правила | service test |
| AC4 | Merge не теряет упражнения правил и добирает поля модели | код + combined test |
| AC5 | `/training` и текст-тренировка используют LLM в app | wiring |
| AC6 | `make check`/`-race`/`govulncheck`; спека/README/отчёт; PR | CI |

## 4. Тесты

`TestTrainingExtractor`, `TestTrainingExtractorNeedsMore`,
`TestServiceTrainingLLMPrimary`, `TestServiceTrainingLLMQuestion`,
`TestServiceTrainingLLMFallbackToRules`; live-проверка на Ollama
(qwen2.5:3b) — извлекает тип/дату/RPE/кардио/4 упражнения.

## 5. Ограничения/что дальше

- Small-модель может ошибаться в деталях; правила+валидация+merge страхуют.
- Разбор тренировки vs предыдущей и следующая тренировка с числами — следующий
  инкремент (FR-3.3/U8–U9).
- Внешний API: текст тренировки уйдёт провайдеру, если выбран `LLM_MODE=api`
  (приватность — осознанная настройка).
