## 🔴 BUG-1. Тренировочный отчёт перезаписывает машинно-читаемые данные

**Где:** `internal/intake/training_service.go` (`persistTraining`) →
`internal/store/report_writer.go` (`WriteTrainingReport`) →
`internal/store/training_history.go` (`parseTrainingSession`).

**Суть.** При сохранении тренировки порядок такой:

1. `SaveTraining` пишет «generic»-шаблон с секциями `## Упражнения`,
   `## Итог`, `## Самочувствие`, `## Боль`, `## Зона готовности` и т.д.
   Именно эти секции умеет парсить `store.TrainingSessions`/`parseTrainingSession`.
2. `TrainingReport` генерирует «дневник-отчёт», а `WriteTrainingReport`
   **полностью заменяет** файл отчётом с другими заголовками:
   `## Утренние показатели`, `## Основные упражнения` (таблица),
   `## Общая статистика`, `## Кардио-дополнение`, `## Анализ`, `## Прогрессия`.

В результате после первого же сохранения файл тренировки больше **не содержит**
`## Упражнения`/`## Итог`/`## Боль`. `parseTrainingSession` не находит эти секции
и теряет упражнения, RPE, длительность, калории, кардио и боль.

**Последствия (наблюдаемо в реальном файле `2026-11-13_ulichnaya.md`):**

- Markdown-канон тренировки перестаёт быть машинно-читаемым: `parseTrainingSession`
  возвращает только `Date/Kind/Person/Done`, без упражнений/RPE/длительности/
  калорий/кардио/боли.
- `TrainingReply`/`analysis.NextSession` на reader **без SQLite-индекса** (CLI,
  тесты, fallback при недоступном индексе) видит историю с пустыми упражнениями:
  «Объём: … (было 0, …)», нет детекта роста RPE → нет deload.
- После рестарта `historydb.Rebuild` читает `reader.TrainingSessions` из Markdown
  и перекладывает ту же потерю в SQLite read-model → таблица «Прогрессия
  (последние 6 …)» деградирует: прошлые строки становятся `—`.
- В пределах одного живого процесса потерю маскирует write-through в SQLite
  (payload с полными упражнениями); это делает баг «мигающим» и трудным для отлова.

**Почему тесты не поймали:** `TrainingSessions` тестируется на generic-шаблоне,
а `WriteTrainingReport` — на самом отчёте; сквозной связки «save → report →
TrainingSessions» нет.

**Варианты фикса (нужен один):**

1. Научить `parseTrainingSession` читать **и** отчётный формат:
   `## Основные упражнения` (markdown-таблица), `## Общая статистика`
   (`- RPE: 7`, `- Средний пульс: …`), `## Кардио-дополнение`, плюс добавить
   строку `- Длительность: …`/`- Калории: …` в `## Общая статистика`.
2. Либо не перезаписывать generic-секции: `WriteTrainingReport` дописывает отчёт
   как отдельную секцию, а `## Упражнения/Итог/Боль` остаются каноном.
3. Либо сделать SQLite payload единственным источником для анализа и не
   пересчитывать упражнения из отчёта при Rebuild (запретить потерю).

**Регрессия:** тест «save тренировки → `WriteTrainingReport` →
`TrainingSessions` должен вернуть упражнения/RPE/длительность/кардио/боль».

## 🟡 BUG-2. Инвалидация кэша истории по mtime каталога ненадёжна для внешних правок

**Где:** `internal/store/cache.go` (`dirStamp`).

**Суть.** Валидность кэша = `fmt.Sprintf("%d:%d", dir.ModTime().UnixNano(), dir.Size())`.
Внутри процесса writer вызывает `Invalidate`, поэтому свои записи работают. Но
канон Markdown может править **другой процесс** (агент, человек, соседний тул) —
а на файловых системах с грубым разрешением mtime (1 с) или при правке файла без
изменения размера каталога отпечаток может не измениться → кэш отдаёт устаревшие
данные. Симптом: `/status`/`/week` показывают старые HRV/тренировки.

**Фикс:** ключ валидности — хэш имён+размеров+mtime файлов (или явная версия),
либо короткий TTL + подписка на изменения; минимально — документировать, что
внешние правки требуют рестарта (`/reindex`).

## 🟡 BUG-3. Vision-тренировка при отсутствии даты молча пишет «сегодня»

**Где:** `internal/intake/service.go` (`processImages`), `internal/intake/vision_pipeline.go`.

**Суть.** OCR/structured часто не извлекает дату (`date_text` пустой). Тогда
`save()` берёт `s.now()` и кладёт тренировку на сегодня, добавляя лишь
предупреждение в ответ. Реально на тестовом скриншоте дата была **13.11**, а файл
писался **14.11** — исторический тренд сдвигается.

**Фикс:** если `date_text` пуст, не сохранять молча: либо задать один уточняющий
вопрос («какой датой сохранить? вчера/сегодня»), либо использовать дату
Telegram-сообщения как подсказку, либо отдельный OCR-проход только по дате.
Минимально — отдельная строка даты в `## Итог` отчёта, чтобы потерю было видно.

## 🟡 BUG-4. `processText` для сбоя питания отвечает текстом про чек-ин

**Где:** `internal/intake/service.go` (`processText`).

**Суть.** После ввода `LooksLikeNutrition` свободный текст идёт в `SubmitText`.
Если LLM-разбор питания падает, пользователю возвращается:
«Не удалось распознать чек-ин. Напиши в формате: сон/HRV/пульс…».
Сообщение вводит в заблуждение.

**Фикс:** формировать подсказку по типу входного текста (`LooksLikeNutrition` →
«не удалось разобрать питание, формат ккал/Б/Ж/У»).

## 🟢 BUG-5. `sanitizeKnowledgeAnswer` схлопывает переносы строк ответа

**Где:** `internal/llm/agent.go` (`sanitizeKnowledgeAnswer`).

**Суть.** `answer = strings.Join(strings.Fields(answer), " ")` превращает любой
многострочный ответ модели (списки, абзацы) в одну строку, и лишь потом
дописываются «Источники». В `/ask` теряется структура.

**Фикс:** убирать только лишние пробелы/пустые строки, не схлопывать все
переносы; либо санитайзить построчно (URL/DOI/PMID), сохраняя `\n`.

## 🟢 BUG-6. Ошибки чтения отдельных файлов проглатываются

**Где:** `internal/store/reader.go` (`loadCheckinSnapshot`), `internal/store/training_history.go`.

**Суть.** `ReadCheckin`/`os.ReadFile` с ошибкой → `continue` без лога. Один
битый/недоступный файл молча выпадает из истории, и пользователь не знает, что
`/status`/`/week` неполные.

**Фикс:** логировать пропуск с именем файла и ошибкой; в read-model помечать
файл недоступным, а не «нет данных».

## 🟢 BUG-7. Дублирование эвристик «похоже на вопрос»

**Где:** `internal/router/ask.go` (`meaningfulQuestion`) и
`internal/app/app.go` (`looksLikeKnowledgeQuery`).

**Суть.** Две почти одинаковые функции с разными списками терминов; при
расширении одна неизбежно разъедется с другой (уже разошлись по порогам).
**Фикс:** один пакет/функция с единым списком терминов и тестом.
